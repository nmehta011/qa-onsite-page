🔐 Page 4: Consent Gating & Data Privacy


            

                
🍪 Consent State Simulator

                

                    Simulates a CMP (OneTrust, Cookiebot, etc.) the way a real integration should gate this SDK:
                    by deferring injection itself, not by expecting the SDK to self-gate — it has
                    no built-in consent API, so nothing here relies on one. While denied, Inject Property
                    below is blocked. This gate only covers this page's own injector, same as every other
                    page-specific fixture in this app — injecting from a different page's button still loads the
                    SDK into this shared document. The traffic monitor further down watches globally regardless of
                    which button caused it, so it stays a real check either way.
                

                

                

                    
                    
                

            


            


            

                

                    
📡 Pre-Consent Traffic Monitor

                    No violations
                

                

                    Every request this app already recognises as SDK traffic (analytics collector, onsite/invitation/
                    form data, in any tab/frame this app can see) is checked against the consent state above at the
                    instant it fires. A row here means SDK traffic went out while consent was denied
                    — during initial load, or after a revoke this SDK had no way to honour.
                    Monitoring is opt-in: it starts once you set a consent state above. Until then
                    there's no policy to violate, so ordinary sessions that never touch this page stay clean instead of
                    logging every request as a false violation.

♿ WCAG Contrast Audit

                Awaiting property
                
                
                
            

            

            

                Checks every configured colour pair — button text against its background, body text against page background,
                and button fills against their surrounding background — against WCAG 2.1 contrast thresholds. Text pairs need
                4.5:1 for AA (7:1 for AAA); button/UI fills against their background need
                3:1. Computed from the same configured values the Design Validator already reads — nothing new
                is captured, so this works the instant a property is injected, before anything even renders.
            

            

                
Inject a property embed to audit its configured colour pairs. 

            

        


        

            

                
♿ Full Accessibility Audit

                Awaiting property

                SDK this page can actually reach in the DOM. Scope limit: the invitation's own content and the

🔀 Environment A/B Comparison

            

            

                Config Drift Baseline above compares the live property against one anonymous snapshot. This keeps
                multiple named snapshots (e.g. "staging", "prod") side by side and diffs both configuration
                and live findings (blocked forms, design/contrast issues, performance) between any two — answering
                "what's actually different between staging and prod" in one screen instead of a four-step export/import.
                The onsite SDK can only run one instance per page, so this captures sequentially — inject staging, save it,
                purge, inject prod, save it, then compare.

🎛️ Provisions & overrides [0]

                No overrides
                
                
            

            

            

                A provision is a feature flag Medallia sets per property — screen capture, custom parameters, session
                recording and similar. Every one the property carries is listed here, and any of them can be
                overridden in this session to see how the SDK behaves with it flipped, without waiting
                for a configuration change. Overrides are held in this browser and re-applied on the next injection.
                Scope: the SDK re-reads a provision on each check, so an override takes effect for
                everything checked after it — but a provision consulted once while the SDK started up has already been
                read, and needs a re-inject to take effect.

⚡ Performance & Core Web Vitals

                Awaiting injection
                
                
                
            

            

            

                What this specific injection actually costs the page — Cumulative Layout Shift, main-thread blocking time
                and a network waterfall of SDK traffic, all measured over a fixed 10-second window starting the
                instant "Inject Property" is clicked, then frozen. Real
                PerformanceObserver data, not an estimate. The window is bounded on
                purpose: Core Web Vitals are defined over an interval, so measuring cumulatively would let an idle tab
                keep inflating its own score forever. Caveat: long tasks are attributed per document,
                not per function, so work this dashboard itself does during those 10 seconds is counted under "this
                page's own script" alongside the SDK's — treat the iframe-attributed rows as the most clearly
                SDK-caused ones.

🔒 Privacy / PII Leak Scan

                No property injected
                
                
                
            

            

            

                Scans every outbound analytics payload and custom parameter this app has already captured for patterns
                that look like email addresses, phone numbers, SSNs, credit card numbers (Luhn-validated to cut false
                positives) or API keys/tokens. Matched values are shown masked — never the real value — since a report
                that leaks the PII it found would defeat its own purpose. Scope limit: the respondent's
                actual typed answers are unreachable (cross-origin iframe, confirmed elsewhere in this app) — this can
                only see what the SDK sends over the network, not what a person types into the form.
